# Architecture decisions

- Keep the authentication mascot's timeline, pointer tracking, and joint-anchored SVG rig in `AuthCharacter`; its parent passes only semantic state so typing and pointer events do not re-render the form or rig.
- Use Framer Motion's frame scheduler for pose interpolation and a single requestAnimationFrame per pointer sample; this avoids competing render loops and preserves smooth cross-browser transforms.
- AI endpoints live as TanStack server routes at src/routes/api.*.ts delegating to src/server-ai/*; they replaced the Supabase edge functions, and page components (src/views) render client-only because they rely on browser APIs.
- Unlimited-use codes are verified only by server routes against the server-only UNLOCK_CODE secret, so no valid code is bundled into the browser.
- Login, signup, and profile display details use the app's own Lovable Cloud auth (`account-client` re-exports the generated client); keep profile details in user metadata because the live schema has no public profiles table, and never point the app at an external backend.
- Answer verification lives in `src/server-ai/verify/`. The answer streams to the student unchanged; when it ends, `withVerification` (stream.ts) appends a `<verification>` JSON block (types and codec in `src/lib/verification.ts`) before `[DONE]`, and `splitThinking` strips it so copy, export and the history sent to the server stay clean. Levels (`VERIFY_LEVEL=off|basic|standard|strict`, default by mode: fast=basic, accurate=standard, advanced=standard or strict by complexity, panache=strict): basic = free static checks; standard = a small model only transcribes claims (each must quote the answer verbatim or it is dropped) and `claims.ts` decides them numerically; strict = also an independent solve by a different model tier, compared on final results. Code, never a model, decides what is "wrong"; anything unverifiable is reported as not checked, and any verifier failure or timeout must never alter or block the answer. Prompts in `verify/prompts.ts` follow the template-literal rule (no backticks, `${`, or backslashes). Five concerns are covered: image reading (`reading.ts`: the first transcription is compared by code with an independent second reading of the photo, numbers/fractions/exponents/indices/units/symbols/table sizes; wildly divergent readings are reported as not checked, never as an accusation), solution checking (`claims.ts`), precise errors (every issue may carry `where` = verbatim snippet and `expected` = the recomputed value), completeness (question and sub-question labels in `static.ts`, plus a model-reported "missing" that code re-confirms against the answer's own numbering), and method/level conformity (`method` role, strict only, high-confidence quote-backed suggestions shown apart from evidence). Anything that could not be judged goes to `Verdict.unverified` and is shown as «تعذر التحقق»; never turn "could not verify" into a verdict.
- Keep remote assistant tools in the app-hosted OAuth-protected MCP catalog and browser-local tools in page-owned WebMCP registrations; they have different trust boundaries and runtimes.
- UI density: `src/lib/display-scale.ts` estimates a `--ui-scale` (1 to 1.3, phones only, never below 1) from the screen's short side in CSS px, or uses the student's manual choice from localStorage. An inline `<head>` script (`UI_SCALE_BOOT_SCRIPT`, kept identical to the TS functions by `display-scale.test.ts`) sets it before first paint; `UiScaleSync` keeps it applied. `html { font-size }` and the answer font multiply by it, so keep sizes in `rem` (not `px`) when you want them to follow it.
- Keep live camera preview-to-image coordinate mapping in the pure `cameraOverlayGeometry` helper so page-boundary overlays stay aligned with `object-contain` across device aspect ratios.
- Question recognition (`POST /api/recognize` → `src/server-ai/recognize/`): a vision model proposes the page structure (exercises, givens, questions, sub-questions, each with `box_2d` = [ymin, xmin, ymax, xmax] on a 0 to 1000 scale), and `src/lib/recognition.ts` (`buildRecognition`) cleans and checks it in code before anything reaches the UI: coordinates are normalised, a box outside its exercise is dropped, an exercise box is the union of its children, and numbering gaps, duplicate labels, overlapping boxes and a question-points sum that differs from the exercise points are reported as warnings that lower confidence. Never trust a model box or label without going through `buildRecognition`; a part with no reliable box is shown without one, not with a guessed one. In the UI (`QuestionMapPanel`) choosing any question crops its whole exercise (givens come first) and writes the request into the composer; cropping is done in the browser (`cropImage.ts`).
- Diagram solver (`POST /api/diagram` → `src/server-ai/diagram/`, button "ارسم الشكل" in `AnswerImage`): three narrow vision calls (`mode` = `locate` | `plan` | `redraw`), each checked in code before anything reaches the UI. `locate` returns the figure box, text boxes to erase and the question's instruction (`buildLocation`: a tiny figure is a failure, erase boxes covering most of the figure are all dropped); `plan` receives the figure crop with a red 0 to 1 coordinate grid and returns named points plus additions (line, arrow, polyline, point, circle, angle, label) that `buildPlan` validates (unknown point refs, out-of-figure coordinates, bad arity and degenerate shapes drop that addition with a visible reason); `redraw` returns an SVG that `sanitizeSvg` (`src/lib/svgSanitize.ts`, whitelist parser that rebuilds the SVG) must pass on the server. The browser (`src/lib/diagramSolver.ts`, pure orchestration over injected `Api` and `Raster`) chooses the engine: Engine A (redraw) is accepted only if `compareFigures` (`diagramInk.ts`) says its long strokes match the original's ink (global f1, 8×8 block check so a wrong curve cannot hide behind matching axes, loose text-position check); otherwise Engine B (emergency) uses the original pixels: crop to the figure, erase other text with `eraseKeepingStrokes` (keeps axes/curves that cross the erase box, but letters touching a stroke stay), white-balance, upscale and sharpen. Both engines draw the additions with our own renderer (`additionsSvg`) at a pen width measured from the figure's own strokes, snap flagged points to the real ink, and straighten near-vertical or near-horizontal guide lines. The code never claims the maths is right: the panel says it verifies figure fidelity and drawing positions, not the solution. Snapping places a point on a real line, not necessarily at an exact intersection or along-curve position. Prompts follow the template-literal rule. There is no daily quota on this route (like `/api/annotate-sheet`), but each click costs up to three model calls.
- Live camera sheet frame (`LivePageCamera` → `src/lib/livePageDetection.ts`): `detectLivePage` draws the frame from the dependency-free `jsPageDetection.ts` detector until OpenCV (`opencvPageDetection.ts`, preloaded in the background) reports `isOpenCvReady()`, then prefers OpenCV; an OpenCV error or empty result falls back to the built-in detector, so the frame never depends on the WASM runtime. The OpenCV runtime is always carried inside a `{ cv }` box and never used as a promise's resolution value: Emscripten modules can expose `then`, and resolving or returning such an object loops forever and freezes the page (`opencvLoader.test.ts`). The contour step reduces the convex hull to four corners with a growing tolerance (a bowed or shadowed sheet still gets a frame) and adds a brightness-mask pass when the edge pass finds nothing. The frame's colours are constants at the top of `LivePageCamera`; `smoothCorners` glides small movements and snaps when a corner jumps more than 10% of the frame diagonal. Two touching pages (an open notebook) are framed together, because splitting at the spine is not implemented.
